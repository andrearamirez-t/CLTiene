La sesión se centró en el módulo de Transcripciones: se añadió un panel de historial de llamadas por número de teléfono (nuevo endpoint BigQuery con IDs globales), se corrigió la sincronización de ROW_NUMBER() entre todos los endpoints que numeran llamadas, se agregaron las métricas de Duración Real y Turnos, y se mejoró el dropdown para mostrar fecha y teléfono del cliente. Adicionalmente se refinó el prompt de detección de hablantes a la versión 15.

Funcionalidades Nuevas
  • 📋
    Historial de llamadas por teléfono — historial_telefono.py
    Nuevo endpoint GET /api/transcripcion/historial/{telefono} que devuelve todas las llamadas realizadas a un número de teléfono específico con fecha, resultado, asesor, duración real y flag de transcripción disponible.
    Frontend: FiltrosLateral.jsx detecta automáticamente si se está escribiendo un teléfono (regex /^\d{7,15}$/) o si la llamada seleccionada tiene teléfono asociado, y muestra el historial debajo del buscador. Hacer clic en cualquier llamada del historial carga su transcripción en el ChatVisor.
    IDs globales: el historial usa ROW_NUMBER() sobre el mismo dataset filtrado que el dropdown, garantizando que el ID del historial coincida con el ID que carga la transcripción correcta.
  • ⏱️
    Duración Real en panel de métricas
    Se añadió la métrica Duración Real al grid de Análisis Detallado mostrando el tiempo exacto de la llamada (Tiempo__de_Conversacion en formato HH:MM:SS) proveniente del campo [Tiempo de Conversacion] de SQL Server.
    Anteriormente solo existía Duración con valor cualitativo (Corta / Media / Larga / Buzón). Ambas métricas coexisten en el panel.
  • 💬
    Turnos contado desde Transcripcion_V4 + Dropdown con fecha y teléfono
    La métrica Turnos ahora se calcula en tiempo real desde Transcripcion_V4 contando ocurrencias de [Asesor] y [Cliente] con REGEXP_EXTRACT_ALL, en vez del campo pre-calculado Num_Turnos_V4 (que era 0 en muchos registros anteriores al campo).
    El dropdown "Seleccionar llamada" ahora muestra FECHA · Resultado · Asesor · Teléfono en lugar de #ID · Resultado · Asesor.

Bugs Críticos Corregidos
  • 🔢
    IDs desincronizados entre dropdown, métricas y análisis IA
    El dropdown (llamadas.py) filtraba con COALESCE(Transcripcion_V4, transcripcion) IS NOT NULL, pero metricas.py y get_llamada_context numeraban todas las llamadas sin filtro. Resultado: seleccionar la llamada #39 del dropdown cargaba métricas de la llamada #39 global (distinta).
    Solución: los tres endpoints ahora usan el mismo WHERE COALESCE(Transcripcion_V4, transcripcion) IS NOT NULL AND {filtros}, garantizando que los ROW_NUMBER() coincidan.
    Métricas de llamada equivocada → Siempre la llamada seleccionada
  • 🗂️
    "No se encontró la llamada" al usar Analizar con IA (#1961)
    get_llamada_context en helpers/utils.py usaba WHERE Transcripcion_V4 IS NOT NULL (sin COALESCE ni filtros del sidebar). Sus ROW_NUMBER() no coincidían con los del dropdown, por lo que la IA buscaba la llamada #1961 en un universo distinto y no la encontraba.
    Solución: alineado el filtro con el mismo criterio que los demás endpoints.
  • 📵
    Historial siempre mostraba "No se encontraron llamadas"
    La query historial_telefono.py referenciaba la columna asesor que no existe en BigQuery (el nombre real es Cuenta). BigQuery lanzaba un error silencioso; el frontend capturaba la excepción y mostraba lista vacía.
    Luego, al usar replace_all para corregirlo, quedó cuenta + Cuenta duplicados (BigQuery es case-insensitive → nuevo error). Se resolvió dejando una sola referencia a Cuenta correctamente.
  • 📞
    Historial usaba Cuenta (nombre del asesor) como teléfono
    El campo cuenta de BigQuery almacena el nombre del asesor (ej. "Jenifer Andrea Rodriguez Cespedes"), no el teléfono del cliente. El campo correcto es Telefono (FLOAT64, ej. 3017384481.0).
    Solución: llamada.py ahora retorna CAST(CAST(Telefono AS INT64) AS STRING) AS telefono en info.telefono, y el frontend usa ese valor para disparar el historial.
  • 🔄
    Estado cuentaActual obsoleto al cambiar de llamada
    Al seleccionar una nueva llamada, si su telefono era nulo, el estado cuentaActual no se limpiaba y el historial mostraba el teléfono de la llamada anterior.
    Solución: setCuentaActual(data?.info?.telefono ? String(data.info.telefono) : null) — siempre actualiza el estado, incluso a null.
  • 📐
    Orden de métricas aleatorio en BigQuery
    UNION ALL sin ORDER BY no garantiza orden en BigQuery. Las métricas aparecían en distinto orden en cada carga.
    Solución: añadida columna ord (1–7) y ORDER BY ord al final de la query. Orden fijo: Resultado → Duración Real → Duración → Plan → Turnos → Saludo → WhatsApp.
  • 🤖
    Prompt v14: "Correcto, señora Rosalía" asignado a CLIENTE
    El modelo asignaba [CLIENTE]: Correcto, señora Rosalía. porque interpretaba "Correcto" como respuesta del cliente. Sin embargo, un cliente nunca se dirige a sí mismo por su propio nombre — esa frase siempre es del ASESOR confirmando y dirigiéndose al cliente.
    Prompt v15: nueva regla explícita "EL CLIENTE NUNCA SE LLAMA A SÍ MISMO POR NOMBRE" + señal "Correcto/Exacto/Entendido, señora/señor [Nombre] → ASESOR" + ejemplo concreto del caso.

Flujo del Historial por Teléfono
Opción A — Búsqueda manual
El usuario escribe un número (7–15 dígitos) en el campo de búsqueda → esTelefono() retorna true → se hace fetch a /api/transcripcion/historial/{tel} → aparece el historial.
Opción B — Selección del dropdown
El usuario elige una llamada del dropdown → agentID cambia → useEffect fetcha /api/transcripcion/llamada/{id} → respuesta incluye info.telefono → setCuentaActual(telefono) → el historial se carga automáticamente.
Clic en llamada del historial
El usuario hace clic en una tarjeta del historial → changeAgent(h.id) con ID global → se cargan transcripción + métricas de esa llamada específica en el ChatVisor y el panel de métricas.
