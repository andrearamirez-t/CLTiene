Análisis automáticos disponibles

El Dashboard Analytics de CL Tiene Soluciones es una plataforma web full-stack que extrae semanalmente los registros de llamadas del SQL Server de la CUN, los procesa mediante un pipeline de análisis de texto (V4) y los publica en un dashboard interactivo con filtros dinámicos, gráficas de rendimiento y siete módulos de análisis con IA generativa (gpt-4o). El sistema permite a los supervisores identificar patrones operativos, evaluar la calidad de atención y tomar decisiones basadas en datos actualizados cada semana.

Módulo Transcripciones — Endpoints de Datos

Invariante crítico: todos los endpoints del módulo de Transcripciones que asignan un ID a una llamada deben usar exactamente el mismo WHERE: COALESCE(Transcripcion_V4, transcripcion) IS NOT NULL AND {filtros}. Cualquier divergencia causa que el ID #N del dropdown apunte a una llamada diferente en métricas, IA o historial.

EndpointArchivoRol
GET /api/transcripcion/llamadas llamadas.py Dropdown: opciones con ID global. Muestra FECHA · Resultado · Asesor · Teléfono
GET /api/transcripcion/llamada/{id} llamada.py Transcripción completa + info con resultado, asesor, teléfono (FLOAT64 → INT64 → STRING)
GET /api/transcripcion/metricas/{id} metricas.py Panel métrico: Resultado, Duración Real, Duración, Plan, Turnos (desde V4), Saludo, WhatsApp. Acepta FilterModel
GET /api/transcripcion/historial/{telefono} historial_telefono.py Todas las llamadas al número dado con IDs globales. Sin filtros de sidebar (muestra historial completo del cliente)
Patrón ROW_NUMBER — sincronización de IDs
# Todos los endpoints usan este mismo CTE base: WITH id_provisional AS ( SELECT ROW_NUMBER() OVER (ORDER BY Fecha ASC) AS id, * FROM `desarrollo-investigaciones.call_center.cltiene_llamadas_procesadas` WHERE COALESCE(Transcripcion_V4, transcripcion) IS NOT NULL AND {filtros.get_query()} -- MISMO filtro en los 3 endpoints ) SELECT * FROM id_provisional WHERE id = {id}
Historial de llamadas por teléfono — flujo
DisparadorCondición en FiltrosLateral.jsxResultado
Usuario escribe número esTelefono(inputValue) — regex /^\d{7,15}$/ Fetch a /historial/{numero}; oculta dropdown de llamadas
Selección en dropdown cuentaActual ≠ null (viene de info.telefono de la llamada seleccionada) Fetch automático a /historial/{telefono_de_llamada}
Clic en tarjeta del historial changeAgent(h.id) donde h.id es el ID global de BigQuery Carga esa transcripción en ChatVisor + métricas actualizadas

⚠️ Telefono se almacena como FLOAT64 en BigQuery (ej. 3017384481.0). La comparación requiere CAST(CAST(Telefono AS INT64) AS STRING) = '{tel}'.

Limitaciones Conocidas y Deuda Técnica

La mayoría del límite está upstream (lado CUN / proveedor), no en nuestro código. Nuestro pipeline blinda lo que puede (dedup, COALESCE, parse de fechas), pero no puede arreglar datos que llegan mal en origen.

LimitaciónImpactoPalanca / responsable
Calidad del STT (techo) faster-whisper medium + beam_size=1 + VAD agresivo → ~1 de cada 3 transcripciones llega inseparable / con palabras deformes. La separación de hablantes solo puede ser tan buena como el texto. CUN (Juan Manuel): subir a large-v3, beam_size=5, ablandar VAD.
Ventas inferidas infladas Resultado_Llamada='Venta' por regex (734) está muy sobreestimado; la venta real se cierra fuera del audio. Por eso se muestra como "Posibles ventas". Venta real = Zoho CLTIENE_VENTAS (Fase='Cerrado Ganado', ~10–15/mes). Pendiente de integrar.
Estado_de_Gestion vacío Viene nulo desde el origen (Sergio nunca lo llenaba) → sin él no hay venta real ni "Estados Prospectos". CL Tiene: llenarlo, o marcar venta sí/no + zoho id en el Excel.
Cruce audio ↔ Excel pierde ~40% La llave de 3 variables (agente+celular+fecha) solo cruza ~60% de las llamadas → huecos de datos. CUN (Juan Manuel): migrar a la llave única WAP (Identificador único).
No contestadas se pierden El SQL solo trae ANSWERED (las NO ANSWER/BUSY se botan al no tener audio) → "Total Marcaciones" subcontado >50% y la contactabilidad real mal medida. CUN: incluir las filas NO ANSWER/BUSY (metadata sin audio) en CLTIENE_LLAMADAS.
Hora 00:00:00 ~3.9k registros perdieron la hora del día (va en el nombre del archivo, no en el timestamp). Mitigado (excluidos de la moda del KPI). Recuperable en origen parseando el filename (Juan Manuel).
Contacto Efectivo ~6% mal clasificado Se infiere de la transcripción → hereda los errores del STT (conversaciones reales que el STT no separó cuentan como "Sin Contacto"). Se corrige solo al mejorar el STT (misma palanca).
Cédula no viene en el origen Sin cédula no se puede cruzar CRM (Zoho) ↔ llamadas de forma limpia. S3 (proveedor): agregar la cédula a la estructura del audio.
Proceso manual frágil El envío del Excel + la clasificación servicio/venta dependían de una persona (Sergio, salió 16-jul). Steven cubre solo salientes. Automatizar con Airflow dentro de la red CUN (Santamaría); el pipeline se agrega como PythonOperator.

Cómo se Calculan las Columnas de la CUN

Aclarado en la reunión de BD del 1 de julio de 2026 con Juan Manuel Marín (COE analítica). Estas columnas provienen de un proceso independiente del pipeline V4 de DivergencyAI: un notebook (Proceso llamadas CL Tiene.ipynb) que corre un LLM local con Ollama sobre las transcripciones. No usa GPT-4o-mini — usa qwen2.5:7b-instruct con temperatura 0.

⚠️ Hallazgo crítico: efectiva = 1 NO significa venta. Es un score de calidad del asesor: la llamada cumplió ≥80% de un checklist de 7 categorías. Es completamente distinto de Resultado_Llamada = 'Venta' (que sí detecta ventas reales, generado por nuestro pipeline). No deben usarse como sinónimos en ningún KPI.

Las 7 categorías de calidad (Ollama, cada una 0/1)

El LLM lee la transcripción y devuelve un JSON con 1 si la categoría aparece de forma clara, 0 si no:

ColumnaQué evalúa el LLM
saludo_inicialEl asesor saluda / se presenta
identificacion_clientePide o confirma datos del cliente (nombre, documento, titularidad)
comprension_problemaExplora el motivo / necesidad del cliente
ofrecimiento_solucionPropone servicios o soluciones concretas
manejo_inquietudesAtiende dudas / objeciones (precio, cobertura, condiciones)
cierre_servicioCierre / agradecimiento / confirmación final
proximo_pasoIndica la acción siguiente (agendamiento, WhatsApp, técnico se comunica)
Fórmula de efectiva
# % de categorías cumplidas puntaje = sum(7_categorias) / 7 # efectiva = 1 solo si cumple 80% o más (mínimo 6 de 7) efectiva = 1 if puntaje >= 0.8 else 0
Columnas de sentimiento (TextBlob / NaiveBayes, NO el LLM)
ColumnaCómo se calcula
polaritySentimiento con TextBlob (−1 a 1)
subjectivitySubjetividad con TextBlob (0 a 1)
clasificacionpositivo si polarity≥0.1, negativo si ≤−0.1, neutro en medio
confianzaProbabilidad del clasificador NaiveBayes
palabrasConteo de palabras con regex \b\w+\b sobre la transcripción
Otros hallazgos de la reunión
  • Tiempo de Conversación viene del Excel que envía CL Tiene, no se calcula del audio → puede no coincidir con la duración real de la conversación. La CUN solo cruza (join) ese Excel con la transcripción por fecha + agente.
  • Transcripciones entrecortadas = llamadas de pocos segundos donde el STT solo alcanza a capturar el saludo. Es esperado, no un bug. Se puede acordar un umbral mínimo de duración para descartarlas.

  • Salientes vs Saliente = error de nomenclatura del lado CUN, lo corregirá Juan Manuel.
  • Migración a Airflow = se busca eliminar los Excel intermedios y automatizar todo el proceso. Reunión de definición: martes 7-jul-2026.
